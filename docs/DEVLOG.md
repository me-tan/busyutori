# 開発メモ: 既知の課題・未確定事項

## 認識精度による誤選択（最優先）

**症状**: 書いた漢字とは別の字が認識候補に含まれ、それが条件を満たすため
選択肢に出てしまう。プレイヤーが誤って選べてしまう。

**具体例**
- 「研」を書いたのに「砕」が候補に出る（どちらも石を含む）
- 「糸＋布」という存在しない字を書いたら「終」と認識された

**原因**
`KanjiCanvas.recognize()` は常に10候補程度を返す。現在の実装は全候補を
対象に絞り込んでいるため、下位候補で偶然一致する。

**測定結果**（初期テスト23回）
```
全候補の平均      10.0 個
該当候補の平均     0.30 個
該当0個: 18回 / 1個: 4回 / 2個以上: 1回
```
該当が複数出るケース自体は稀。ただし出たときに誤選択が起きる。

### 対策案（実装優先度順）

**A. 候補数を絞る（最も簡単・効果大）**

`judge()` 内で `cands` を上位3つに制限する。1行で済む。

```javascript
const cands = String(KanjiCanvas.recognize('can') || '')
  .trim().split(/\s+/).filter(Boolean).slice(0, 3);
```

副作用: 正しく書いたのに候補から漏れる可能性が上がる。
上位3・5・10で実際に試して、体感の良い値を決めること。

**B. 画数でフィルタする**

KanjiCanvasは書かれたストローク数を保持している。`ref-patterns.js` の各漢字の
パターンデータからも画数が取得できるはず。書いた画数と一致しない候補を
除外するだけで精度が大きく上がる可能性がある。

要調査:
- KanjiCanvasがストローク配列をどこに保持しているか
- `ref-patterns.js` のデータ構造から画数を取れるか

**C. KanjiCanvas自体を改造する**

MITライセンスなので改変可能。認識スコアの閾値を設けて、一定以下の候補を
捨てる、など。

要調査: `recognize()` がスコアを内部で持っているか、外部から取れるか。

### 調べる価値のないこと

以下は検証済みで、いずれも使えない。再検討に時間を使わないこと。

| 手段 | 結果 |
|---|---|
| Chrome Handwriting Recognition API | 日本語が環境非対応 |
| Gemini API（画像で認識） | 平均3.5秒。精度も不十分 |
| Google Input Tools 手書きAPI | 正式公開APIではなく無断利用になる |
| モジナビの内部API | 同上 |
| ユーザーローカル手書き認識API | 資料請求フォーム経由で日数が読めない |
| tegaki-kaki 方式 | 精度が不足 |
