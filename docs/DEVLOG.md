# 開発メモ: 既知の課題・未確定事項

## 認識精度（CNNモデルに差し替え済み。実機での確認が残っている）

**もともとの症状**: 書いた漢字とは別の字が候補に出て誤選択できてしまう。
逆に、正しく書いたのに候補から漏れることも多かった。

**原因**: KanjiCanvasのテンプレート照合は常用漢字2136字を相手に順位を付け、
`judge()` がその上位数件に切ってから「部首を含むか」を判定していた。つまり
答えの数十字に絞れるはずの問題を2136択で解かせていたので、正しく書けていても
無関係な字に押し出されるだけで落ちた。加えて画数フィルタ（基準の−2〜+1画）と
筆順依存があり、続け書きや筆順違いで正解が候補から消えていた。

**対応**: 認識をDaKanjiの単漢字CNN（ONNX、画像ベース）に差し替え、候補を
「答えになりうる字」に絞ってから順位を付けるようにした。筆順・画数の制約は
無くなった。仕組みとしきい値は[GAME_DESIGN.md](GAME_DESIGN.md)の「手書き認識」を参照。

**合成ストロークでの確認**（`judge()` を通した結果。ヘッドレスChrome）

| 入力 | 結果 |
|---|---|
| 「本」「林」（部首:木） | 正解。確率0.93〜0.96 |
| 部首「木」そのもの | 「木」と認識して正しく却下（以前は「末」を正解にしていた） |
| 「日」（部首:木） | 「日」と認識して却下 |
| でたらめな線 | 候補内の最高確率が0.0まで落ち、却下 |

正解の確率は0.03〜0.99、部首違い・でたらめは0.0。桁で分離しているので
しきい値には余裕がある。

**追加で見つかった問題**: 「変な字を書いても何かしら認識されて正解になって
しまう」ことがある。CNNはソフトマックスの性質上、学習していないパターン
（でたらめな線）にも必ずどれかのクラスへ確率を割り振ってしまうため、確率の
しきい値だけでは弾ききれない。ランダムな殴り書きで再現したところ、候補を
部首で絞った状態でも100回中4〜7回が誤って正解扱いになった。

**対応1**: 書いたストローク数（≒画数）と候補の画数が離れすぎている候補を
別途落とすフィルタを追加（`strokeCountOk()`、[GAME_DESIGN.md](GAME_DESIGN.md)参照）。
画数データはKanjiCanvasの`ref-patterns.js`から抽出（`frontend/data/stroke-counts.json`）。

**対応2**: フォント描画した「正しい字」（候補プール内で常に0.95以上）と、
画数フィルタを素通りした殴り書き（大半0.3未満だが裾は長い）の確率分布を
実測したうえで、`OCR_MIN_PROB`を0.005→0.2、`OCR_POOL_RATIO`を0.15→0.4に
引き上げた。合成1000件の誤受理率は 4〜7% → 約1.8%（画数フィルタのみ）→
**約0.3%**（しきい値も込み）まで下がった。正しい字（最低0.95台）は一切
弾かれていない。

**誤受理の中身を見た結果**: 残った数件を1つずつ確認したところ、確率が
0.13〜0.81と幅広く、しかも**画数がほぼ正確に一致していた**（18画の候補に
17〜18画で書いた殴り書き、等）。つまり画数フィルタの許容幅（続け書き対策の
ゆとり）をすり抜けたわけではなく、たまたま書いた画数そのものが合って
しまったケース。加えて、これは`金`（鎖・鎌）、`辶`（迷）、`艹`（藤）、`氵`（淡）
のような**画数の多い・複雑な部首で起きやすい**傾向が見えた。ランダムな
線が多いほど、正規化後の64×64画像が複雑な字の「見た目の密度」に偶然
似てしまいやすいと考えられる。この知見を反映して`STROKE_UNDER_RATIO`も
0.35→0.25に締めている。

**それでも0にはならない理由**: 上記のうち確率0.81のケースなどは、
しきい値をどれだけ上げても消えない（正しい字の確率帯と地続きになって
しまうため）。これはソフトマックス分類器が「未知のパターン」という
出力を持たず、必ず学習済み6507クラスのどれかに投票してしまう構造上の
限界で、確率・画数どちらのフィルタを詰めても埋めきれない。さらに詰める
にはOOD（out-of-distribution）検出が必要で、別途モデルの学習が要る
規模の変更になる。

**残っている確認**: 上記はすべて合成ストローク・合成フォント描画での
実測で、**実際の手書き（スマホで指書き、子どもの字）では未検証**。
`OCR_MIN_PROB` / `OCR_POOL_RATIO` / `OCR_AMBIGUOUS` / `STROKE_UNDER_RATIO` /
`STROKE_TOLERANCE_OVER` は実機で書いて詰める必要がある。特に画数フィルタは
「続け書きでどれだけ画数が減るか」「殴り書きでどれだけ誤受理が起きるか」の
実際のバランスがまだ実機データに基づいていない。初回ロードの重さ
（wasm約11MB＋モデル2.2MB）もモバイル回線で実測すること。

### 調べる価値のないこと

以下は検証済みで、いずれも使えない。再検討に時間を使わないこと。

| 手段 | 結果 |
|---|---|
| Chrome Handwriting Recognition API | ChromeOS限定かつ英語のみ（2026年9月時点も変わらず） |
| Google ML Kit Digital Ink | 日本語対応・無料だがAndroid/iOS SDKのみ。Web不可 |
| MyScript Cloud REST API | 精度は最高峰だが月2,000件以降は1,000件あたり$10。1試合で10〜20回判定するので釣り合わない |
| Gemini API（画像で認識） | 平均3.5秒。精度も不十分 |
| Google Input Tools 手書きAPI | 正式公開APIではなく無断利用になる |
| モジナビの内部API | 同上 |
| ユーザーローカル手書き認識API | 資料請求フォーム経由で日数が読めない |
| tegaki-kaki 方式 | 精度が不足 |

### 使われなくなったもの

`frontend/js/vendor/ref-patterns.js`（6.7MB）はKanjiCanvasのテンプレート
データで、もう読み込んでいない。`frontend/dev/hanteitest*.html` は旧エンジン
時代の判定テストで、同じフォルダにこれらをコピーして使う前提のまま残してある。
