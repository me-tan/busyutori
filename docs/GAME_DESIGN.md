# ゲーム設計

## コンセプト

提示された部首を含む漢字を、制限時間内に手書きで書き出すゲーム。
一度使った漢字は同じ試合・同じセッション中は二度と使えないため、続けるほど
自分の知識の底が試される。

実現したいことは3つ。

1. **漢字を覚える作業を勝負に変える。** 相手に勝つために漢字を思い出そうとする
   過程が、そのまま練習になる。友達と競える形にすることで、勉強のために時間を
   作らなくても楽しく漢字に触れられる。
2. **部首の意味を意識するきっかけを作る。** 部首は漢字の意味を表しているのに、
   テストのために覚えるものになりがち。「氵」から漢字を探す作業を繰り返すうちに、
   水に関係する漢字が集まっていることに自然と気づける。
3. **知らない漢字に出会う仕組みを入れる。** 勝負がついたあとに、使われなかった
   漢字を一覧で見せる。ふつうのドリルでは自分が知らない漢字には気づけないが、
   負けた直後なら悔しさもあって印象に残りやすい。

対象は小学生〜高校生。学年配当に応じて出題範囲を切り替える。

「ぶしゅとり」というアプリ名の通り、対戦（誰かと部首を投げ合う）が本作の軸。
起動後の入口は「だれかと対戦する」「ひとりで練習する」の2択で、対戦を先に出す。

## モード

### タイムアタック（一人用・オフライン）

- 制限時間 **30秒**（フロントエンドの `TIME_LIMIT` 定数）
- 正解すると次の部首へ。時間はリセット
- 時間切れで終了。連続正解数がスコア
- 同じ部首が連続しないよう、直近2回に出た部首を避ける
- 未使用漢字が5字未満の部首は出題対象から外れる

### 部首マスター（一人用・オフライン）

- 部首を1つ選び、その部首の漢字をすべて書き出す
- 制限時間なし
- 対象の字数だけ点線の箱が並び、正解すると埋まる
- 全部埋めると「部首マスター」＋所要時間を表示

### オンライン対戦（二人用）

別々の端末にいる相手と、部首を投げ合って対戦する。バックエンド
（`backend/`）がルームと試合の状態を管理する。プロトコルの詳細は
[BACKEND.md](BACKEND.md) を参照。

対戦の入り方は3通り:
- **ランダムマッチング** — 同じ難易度で待っている誰かと自動で組む。20秒
  （フロントエンドの`QUICKMATCH_TIMEOUT_SECONDS`）以内に見つからなければあきらめる
- **部屋を作る/入る** — 部屋コードを知っている相手（友だち）と対戦する
- **フレンドを対戦に誘う** — フレンド画面から1タップで誘う（[USERS.md](USERS.md)参照）

```
[攻撃] 手番プレイヤーに部首の候補5つを提示 → 1つ選んで相手に投げる
  ↓
[防御] 相手は30秒以内に、その部首を含む漢字を手書きで答える
  ↓
  ├ 成功 → 攻守交代して続行
  └ 失敗（時間切れ） → 攻撃側の勝ち。結果画面へ
```

- 使用済み漢字は試合全体で共有（攻撃側・防御側どちらが書いた字も対象）
- 学年範囲（初級/中級/上級）はルーム作成時に決める
- 判定（部首を含むか・未使用か）はサーバー側が最終判断する
  （クライアント側の判定はプレイヤーへの候補表示のためだけに使う。クライアントを
  改造されても不正解が通らないようにするため）
- 決着時、最後に投げられた部首についてタイムアタックと同じ「未使用漢字の提示」
  （下記）を行う

## 共通の正解の条件

- 出題された部首を含む
- まだ使われていない

難易度（学年範囲）は出題する部首を絞り込むためだけに使う。選んだ難易度より
上の学年の字で答えても、その部首を含んでいて未使用なら正解にする
（「初級なのに小4の字はダメ」という制約は設けない）。

### 不正解時のメッセージ

原因を明示する（黙って弾かない）。

| 状況 | 表示 |
|---|---|
| 既に使った | 「『海』はもう書きました」 |
| 該当なし | 「その部首を含む漢字が見つかりません」 |

## 難易度

| 難易度 | 範囲 | 出題可能な部首 |
|---|---|---|
| 初級 | 小1〜小3 | 12種 |
| 中級 | 小1〜小6 | 19種 |
| 上級 | 常用漢字すべて | 23種 |

低学年ほど該当漢字が少ないため、学年ごとではなく累積範囲とする。

## 結果画面（本作の中心機能）

最後に出題された部首について、使われなかった漢字を提示する。

```
氵を含む漢字は、まだ 37 字ありました

[海 うみ 小2] [池 いけ 小2] [泳 およぐ 小3] ...

あなたが書けたのは 汽 活 の 2 字
```

- 学年順に並べる
- 読みは訓読みを優先（「うみ」の方が「かい」より思い出しやすい）
- 上限24字、それ以上は「ほか◯字」

## 手書き認識

画面への描画とストロークの記録はKanjiCanvasを使い、**認識そのものは
CNNモデル**（`frontend/js/recognizer.js`）が行う。KanjiCanvasのテンプレート
照合（`recognize()`）はもう使っていない。

```javascript
KanjiCanvas.init('can');          // canvas の id を渡して初期化
KanjiCanvas.deleteLast('can');    // 一画取り消し
KanjiCanvas.erase('can');         // 全消去

// 認識。allowed（Set）を渡すと、その中だけで順位を付けた pool も返す
const { top, pool } = await KanjiRecog.recognize(KanjiRecog.strokesOf('can'), allowed);
// top  … 全6507字での順位 [[漢字, 確率], ...]
// pool … allowed の中での順位。同じ確率値で、対象外の字を取り除いただけ
```

### モデル

[DaKanji単漢字認識モデル](https://github.com/CaptainDario/DaKanji-Single-Kanji-Recognition)
（MIT、ETL文字データベース＋KanjiVGで学習）をONNX Runtime Webで動かす。

- `frontend/models/kanji-recog.onnx`（int8、2.2MB）と同ラベル（6507字、区切り
  なしで1文字＝1クラス）。出題対象の1542字のうち未収録は4字だけで、これは
  字体改定前の字形（剥→剝など）に読み替えて対応している（`VARIANTS`）
- ランタイムは `frontend/js/vendor/ort/`。`<script>`タグで読むのでビルドは不要
- **画像を見るモデルなので筆順・画数に依存しない**。これが差し替えの主目的

### 前処理が精度を左右する

モデルは「枠いっぱいに中央寄せされた字」しか想定していない。小さく書いたり
隅に寄ったりすると当たらなくなるため、`renderInk()` で**書いた範囲を切り出して
中央に置き直し**、白地に黒ではなく**黒地に白線**で描いてから渡している。
縦横比は保つ（「一」のような字が潰れないように）。

### 候補は「答えになりうる字」に絞ってから順位を付ける

6507字の中で順位を付けると、正しく書けていても無関係な字に押し出される。
出題された部首を含む未使用の字だけを `allowed` として渡し、その中で順位を
付けることで取りこぼしを防いでいる。

ただし絞ると「必ず何かが1位になる」ので、`index.html` 側で3つのしきい値を
かけている（いずれも実機でのチューニング対象）。

| 定数 | 役割 |
|---|---|
| `OCR_MIN_PROB` | これ未満は「認識できなかった」として捨てる |
| `OCR_POOL_RATIO` | 答えにならない字のほうがこれ以上強ければ、弱い候補を正解にしない |
| `OCR_AMBIGUOUS` | 2位が1位に近ければ自動確定せずプレイヤーに選ばせる |

`OCR_POOL_RATIO` は誤受理を防ぐためのもの。たとえば部首「木」の問題で「木」
そのものを書いたとき、「木」は答えに含まれないため、形の似た「末」が候補の
1位になってしまう。全体1位（木）と比べて弱すぎる候補は正解にしない。

現在の値（`OCR_MIN_PROB=0.1`, `OCR_POOL_RATIO=0.4`）は、フォント描画した
「正しい字」が候補プール内で常に0.95以上になる一方、殴り書きは画数フィルタを
素通りしても大半が0.3未満に収まる、という実測分布から選んでいる。合成400件の
テストで誤受理は約0.5%まで下がったが、**ゼロにはならない**。まれに、殴り書きが
たまたま実在の字に近い形になり、モデルが本気で（確率0.9など）誤認識することが
あるため。これはソフトマックス分類器が「未知のパターン」という出力を持たず、
必ず学習済みクラスのどれかに投票してしまう構造上の限界で、しきい値の調整では
埋めきれない。さらに詰めるならOOD（out-of-distribution）検出の仕組みが要る。

### 画数フィルタ（`STROKE_COUNTS` / `strokeCountOk()`）

CNNはソフトマックスの性質上、学習していないパターン（でたらめな線）にも
必ずどれかのクラスに確率を割り振ってしまう。確率のしきい値だけでは、殴り書きが
たまたま候補の1つに強く一致して誤って正解扱いになることがある（実測: 候補を
部首で絞った状態でもランダムな殴り書き100回中1〜数回発生）。

これを補うため、書いたストローク数（≒画数）と候補の画数が離れすぎている字を
別途落としている。データは`frontend/data/stroke-counts.json`（KanjiCanvasの
`ref-patterns.js`から抽出した字→画数、2213字、ゲームの対象1540字中1539字を
カバー）。

少なく書いた側の許容は画数に**比例**させている（`STROKE_UNDER_RATIO`）。固定の
画数で許容すると、画数の少ない字にはガバガバに、多い字にはきつすぎることに
なるため。続け書き（画をつなげて書いて1画に数えられてしまう）でも、比例許容の
おかげで妥当な範囲なら正解として通る。多めに書いた側は一律の許容
（`STROKE_TOLERANCE_OVER`）。この3つの定数も実機での調整対象。

## データ仕様（radicals.json）

### 生成元

- **KANJIDIC2** — 学年・読み・康熙部首番号（辞書上の正式な部首）
- **CHISE IDS**（cjkvi-ids）— 漢字の字形分解データ（へん・かんむり等の表示形の判定にのみ使用）

### 構造

```json
{
  "meta": {
    "radicalCount": 62,
    "kanjiCount": 1542,
    "grades": { "1":"小1", ..., "8":"中学以降" }
  },
  "radicals": {
    "氵": {
      "name": "さんずい",
      "meaning": "水に関係する",
      "kanji": {
        "2": ["池","汽","活","海"],
        "3": ["氷","決","油", "..."]
      },
      "count": { "all": 111, "elem": 43, "low": 18 }
    }
  },
  "kanji": {
    "海": { "grade": 2, "on": ["かい"], "kun": ["うみ"], "readings": ["うみ","かい"] }
  }
}
```

### 設計判断:「部首」の定義

**KANJIDIC2の康熙部首番号（辞書が定める、その字の正式な部首）に基づいて判定している。**
以前は字形分解（CHISE IDS）だけで「その部品が字形に含まれているか」を機械的に
判定していたが、これだと部首として機能していない偶然の字形一致まで拾って
しまう（例: 「相」が本当の部首である目ではなく木の側にも該当してしまう、
「大・火・金・茶・内」が人（にんべん）の字形と誤認されて紛れ込む）。
本作は部首から漢字の意味を連想する感覚を身につけることを目的の一つに
しているため、こうした誤爆は学習内容として不適切と判断し、KANJIDIC2の
部首番号を一次判定に切り替えた。CHISE IDSは、氵/水・忄/心・扌/手・亻/人・
灬/火・衤/衣・礻/示・犭/犬のように同じ部首番号でも表示形が2通りある場合に、
どちらの字形で出題するかを決めるためだけに使う（例: 部首番号85＝水は、
「氵」の字形を含めば「さんずい」、含まなければ「みず」として出題する）。

トレードオフ: 部首そのものである字（水・木・金・土・人など基礎的な字の多くは
それ自体が部首番号を持つ）は「その部首を含む字」には数えられないため、
特に小学1年で習う漢字は対象漢字がさらに減る（27字→16字）。誤判定を許容して
字数を稼ぐか、正確さを優先するかのトレードオフで、後者を選んだ。

**名前が1つで字形が2通りある部首（刀/刂・玉/王・糸/糹）は、両方の字形をまとめて
1つの部首として表示する。** 氵/水のように学校教育で別々の慣用名がある部首は
別の部首として出題するが、りっとう（刀/刂）・おう（玉/王）・いと（糸/糹）は
慣用名が1つしかなく、片方の字形しか見せないと「初」（衤+刀）のような字が
りっとうの対象だと気づけない。このため表示だけ両方の字形をまとめ、部首そのもの
にあたる`刀`・`玉`・`糸`自身は他の部首と同様に出題対象から除外している。

この判定方針に伴い、以下の調整を行った。

- **呼称から位置を示す語を除いた。**
  「つちへん」→「つち」、「きへん」→「き」。
  土は左だけでなく上下にも来る（王・主・寺）ため、「へん」と呼ぶと嘘になる。
  一方、氵・艹のように位置が固定されている部首は「さんずい」「くさかんむり」のまま。
- **意味がばらつく部首の説明文を「〜の形が入っている」に変えた。**
  口を「口や声に関係する」とすると京・高・船が説明できない。
  「口の形が入っている」なら全て正しい。
- **表示形の判定（CHISE IDS）は1階層の分解のみ使う。**
  再帰的に分解すると「語」が口にも該当してしまい直感とずれる。

### 設計判断: 異体字の統合と分離

**統合したもの**（同じ形でコードが違うだけ）

```
⺮→竹, 糸→糹, ⺡→氵, ⺘→扌, ⺅→亻, ⺾/艸→艹,
⻌/辵→辶, ⺖→忄, ⺬→礻, ⻂→衤, ⻖/⻏→阝,
⺩/玉→王, ⺨→犭, ⺣→灬, ⺼→月, 刀/⺈/⺉→刂,
攴/⺙→攵, ⺧/牜→牛
```

**あえて分離したもの**（形が違い、直感的に別物）

| 分離 | 理由 |
|---|---|
| 亻 / 人 | 亻92字は全てにんべん。人16字は傘・企・全・舎など。統合すると大・火・金がにんべん扱いになる |
| 扌 / 手 | 扌86字は全ててへん。手6字は挙・拳・掌・摩・撃 |
| 火 / 灬 | 灬18字（点・照・熱・黒・馬・魚・鳥）は火に見えない |
| 衤 / 衣 | 衤10字（初・補・被）、衣7字（製・裁・装） |
| 礻 / 示 | 礻12字（社・神・福）、示8字（祭・票・禁） |
| 犭 / 犬 | 犭13字（犯・独・猫）、犬10字（器・状・献） |

**除外したもの**

- 肉（腐1字のみ）
- 牜（0字。牛に統一）

### データの再生成

生成スクリプトは `scripts/build_radicals.py`。外部ソース（KANJIDIC2由来データ、
cjkvi-ids）が必要（スクリプト冒頭のコメント参照）。`RADICALS` 辞書に部首と
名称・説明を列挙し、`VARIANT` で異体字を統合している。出題対象の部首は
手作業でキュレーションしている（機械的な集計には「一」「丿」等の直感的でない
部品が混ざるため）。

## コーディング方針

- フロントエンドはビルド不要のバニラJSを維持する。フレームワークを追加しない
- 外部ライブラリを追加しない（KanjiCanvasと、手書き認識のONNX Runtime Web以外）
- バックエンドは対戦の状態管理に必要な最小限の依存だけを使う
  （FastAPI + Uvicorn。DBは使わない。状態はメモリ上のみ）
- 定数は各ファイルの先頭にまとめる
- 日本語のUIテキストは、小学生が読める語を使う
